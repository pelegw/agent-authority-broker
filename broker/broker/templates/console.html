Plugins

Each target system is a plugin running in its own container. Configure it, enable it, connect it. Disabling a plugin removes its tools on the next request and holds its queued actions; its credentials stay inside the plugin. Add plugin installs one from its own repository, after you review what it can do.

Agent keys

One key per agent. A key's authority is its capabilities (its grants), limited to the enabled, connected plugins. Its ceiling (role) never grants anything: it only caps the capabilities, and is shown here only when it is lower than full. Delegated keys show the chain they came from.

Delegations

Keys that agents created for their sub-agents, each under the key it came from. No human approves a delegation: a child holds only what was carved out of its parent's authority, and that is checked again on every call. You act after the fact: disable or revoke any key, and every key below it stops at its next call.

    Hidden resources

    A hidden resource is invisible to every agent key: absent from lists and a 404 on direct access, exactly like a resource that does not exist. What is stored is the resource's id, so renaming it never unhides it. Per-key denies live on the key (Agent keys, Edit).

    Settings

    Operator settings, stored in the broker's database. A change applies on the next request unless it says otherwise. A value in the environment file is only the default that a change here overrides; Reset goes back to it.

    What lives in files

    These are deliberately not editable here. Some are bootstrap secrets that must exist before the database can be read. The others decide how the broker is exposed and fail closed at boot, so a hijacked console session must not be able to weaken them. They are set in the broker's .env (written by scripts/init_secrets.py) or in the compose files: change them there and restart. Secrets show only whether they are set, never their value.
